    How CloudGuard works

    CloudGuard checks infrastructure code for security mistakes before it gets deployed. A proven static analyzer finds the problems, and a language model explains them in terms of your file and writes a corrected version.

    What happens when you scan

    1. Checkov runs the policies

      You can paste one file, upload a zip, or link a public GitHub repository or folder. Configuration files are picked out (Terraform, CloudFormation, Kubernetes, Helm, Compose, Dockerfiles) and everything else is ignored. Checkov, an open-source analyzer with over 1,000 policies, then reports each resource that fails a policy, with the file and lines involved. The same files always give the same findings.

    2. The findings get explained

      The files and Checkov's findings go to a language model: gpt-oss-120b on Groq for free explained scans, or the model you pick with your own API key. For each finding it says what is actually at risk in your code and which setting to change. It also points out problems no policy covers, such as passwords in a Docker Compose file. Those are listed separately and don't affect the score.

    3. Earlier fixes are checked

      Findings are turned into embeddings by a small open model (bge-small) that runs on this server, and compared with findings from your own earlier scans stored in PostgreSQL with pgvector. The closest matches and the patches written for them are used as examples, which keeps fixes consistent between files. Only your scans are searched.

    4. A patch is written

      The model rewrites each file with its findings addressed and marks changed lines with a # FIXED: comment. The page shows each patch as a diff against the original. For projects, the files with the most serious findings are patched first.

    5. The scan is saved

      It goes into your history. A copy of the original and patched files is written to a private S3 bucket.

    Free explained scans and your own key

    Checkov results are always free. Explanations, extra review findings and patches use a language model, so each visitor gets a few explained scans per day on this site's Groq account. After that, scans still run Checkov and show every finding, just without explanations or patches.

    You can also use your own API key from OpenAI, Anthropic, Google, xAI, Groq or Mistral in . CloudGuard lists the models your key can use and suggests one. Scans with your key have no daily limit, cover larger projects, and are billed to your account by the provider. Diagram checks always use your own key.

    How the score works

    Only Checkov findings count, so the score is the same every time you scan the same file. CloudGuard rates each Checkov policy itself, because the open-source release doesn't include severities: public access and secrets are critical, missing encryption is high, logging and backups are medium, and tags and monitoring are low. Each finding adds points:

    SeverityPoints
    Critical30
    High12
    Medium4
    Low1

    The score is 100 × e−points / 80. The first serious problems cost the most, and a long list of minor warnings can't drag an otherwise sound file to zero. One critical finding gives 69, one high gives 86, and ten low ones give 88. Files Checkov doesn't support, such as Docker Compose, aren't scored.

    Diagram check

    The model you chose in Model settings reads the image and the Terraform together, so it has to be one that accepts images. It reports resources that appear in one but not the other, subnets placed differently, and connections the security groups or route tables don't allow. It doesn't try to read things like IAM permissions or port numbers from a picture. The Terraform also goes through a normal scan. A diagram check uses one of your free explained scans.

    Your data

    • There are no accounts. The first time you visit, your browser gets a random ID in a cookie, and every scan you run is filed under it. Nobody else can list, open or search your scans, and they're never used as examples for anyone else's patch.
    • Because history belongs to the cookie, it won't follow you to another device. Clearing your cookies loses access to it.
    • Clear history deletes your scans and findings from the database. The file copies in S3 aren't linked to your browser and aren't shown to anyone.
    • Checkov and the embedding model run on this server. For explained scans, the files are also sent to the model provider: Groq on the free tier, or whichever provider your own key belongs to. Don't include real passwords or keys in what you scan; swap them for placeholders first.
    • If you add your own API key, it's kept in this browser (or only for the session if you untick "Remember on this device") and sent with each scan over HTTPS. The server hands it to the provider for that request and never stores or logs it. Forget key in Model settings removes it.
    • Repositories are downloaded from GitHub for the scan and not kept, apart from the files saved with your scan.
    • The free-scan counter stores a keyed hash of your IP address, not the address itself.

    Limits

    • Checkov only knows the policies it ships with. Passing every policy doesn't mean a file is secure.
    • Explanations and review findings come from a language model. They can be wrong or miss things, which is why they never change the score.
    • Read a patch before applying it and run terraform plan. A rewrite can change more than the lines it marks.
    • Pasted files can be up to 120,000 characters. Zips can be up to 10 MB and repositories up to 25 MB compressed, with at most 400 configuration files. Diagrams can be up to 8 MB. Scans are rate limited per IP address.
    • The free explanation model has a small per-minute allowance shared by every visitor. Large projects get explanations for the files with the most serious findings, and patches for up to three files. When the model is busy, the scan shows Checkov results and says so.
